## 2. 轮次 1：宏观架构前沿质询

> **Agent**：
> 收到短链系统建设诉求。基于当前工程已存在的 Redis 和 MySQL 基础，已探测到架构起点。当前构建第一轮决策前沿，请针对以下核心架构分歧进行决断：
>
> ❓ **Q1** - **短链核心发号生成算法选型**：
> 针对 20000 QPS 吞吐，如何平衡全局唯一性与短链长度（6~8 字符 Base62）？
> - **选项 A**：基于 Redis `INCR` 步长分段发号器转 Base62。吞吐极高，短链有序且紧凑，但单点依赖 Redis 且易被遍历攻击；
> - **选项 B**：MurmurHash3 + 布隆过滤器冲突重算。无中心化状态，支持无序防遍历，但存在哈希冲突重试开销；
> - **选项 C**：分布式雪花算法 (Snowflake) 高位截断。全内存本地运算，但转 Base62 后长度偏长（10~11 位）。
>
> ➡️ **推荐决策**：**选项 B (MurmurHash3 + 布隆过滤器)**。理由：运营短链必须防撞库遍历，且 MurmurHash3 性能优异，在十亿级数据下通过布隆过滤器可将冲突率压至 0.001% 以下。
>
> ---
>
> ❓ **Q2** - **短链重定向网络跳转状态码**：
> 跳转时应优先照顾客户端缓存还是服务端精准数据分析？
> - **选项 A**：HTTP 301 永久重定向。浏览器强缓存，极大减轻服务端 20000 QPS 压力，但无法精确统计 UV/PV 与客户端访问特征；
> - **选项 B**：HTTP 302 临时重定向。每次跳转均过网关，统计百分百精准，但全部流量打在短链服务上。
>
> ➡️ **推荐决策**：**选项 B (HTTP 302)**。理由：运营系统最核心诉求是精确追踪转化漏斗与点击轨迹，301 缓存会导致数据完全失真。

> **用户**：“采纳你们的推荐：选 MurmurHash3 + 布隆过滤器，跳转用 HTTP 302。”

## 3. 轮次 2：数据流与防击穿前沿质询

> **Agent**：
> 树状态更新：已锁定哈希算法与 302 跳转模式。解锁下游决策前沿：
>
> ❓ **Q3** - **千万级短链读多写少缓存穿透防御**：
> 在 20000 QPS 的 302 跳转场景下，如何防止恶意请求对不存在的短链发起扫库攻击？
> - **选项 A**：空值缓存 + 短 TTL（5 分钟）。简单通用，但大量随机 Key 会侵占 Redis 内存；
> - **选项 B**：网关层预置布隆过滤器拦截 + Redis 缓存击穿互斥锁。完全阻断数据库穿透，但布隆过滤器存在极小误报率。
>
> ➡️ **推荐决策**：**选项 B (布隆过滤器拦截 + 互斥锁)**。理由：工程已引入 Redisson，具备开箱即用的布隆过滤器组件，可直接复用降低内存开销。

> **用户**：“同意选项 B。还有其他问题吗？”

## 4. 构建者反审 (Builder Check) 压力测试

> **Agent**：
> 前沿决策已全部敲定。现在启动**构建者反审 (Builder Check)**，以落地实现者视角进行最后一道防线测试：
>
> 1. **极端异常与故障域**：若 Redis 节点瞬时宕机，网关层布隆过滤器不可用，系统是否会瞬间压垮 MySQL？
>    - *防御预案*：增加 JVM 本地 Caffeine 缓存作为 L1 缓存（TTL 30 秒），Redis 异常时自动降级熔断，禁止直接扫库。
> 2. **异步可观测性**：HTTP 302 每次访问记录埋点日志，若同步写库会显著拉高跳转 P99 时延（从 5ms 恶化至 50ms）。
>    - *防御预案*：埋点数据写入内存队列或 Kafka 异步处理，与主跳转链路物理隔离。
> 3. **回滚与兼容**：MySQL 存储 schema 设计时需对长链接字段预留最大 2048 字符变长文本，并建立 `short_code` 唯一索引。
>
> 上述防御预案已纳入最终契约，请确认。

> **用户**：“考虑得很周到，确认通过！”
