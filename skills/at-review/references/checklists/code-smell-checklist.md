## 1. 审查原则：启发式判断与规范优先

- **仓库明文规约优先**：若仓库在 `AGENTS.md` 或规范中显式允许某种写法，以仓库规约为准，抑制基线坏味道报警；
- **启发式建议而非生硬判罚**：坏味道是设计值得关注的警示信号，需结合业务复杂度做权衡，跳过编译器或 Linter 已拦截的格式琐事。

## 2. Fowler 十二大经典代码坏味道

| 坏味道标识 | 现象特征 | 重构处方 (How to Fix) |
| :--- | :--- | :--- |
| **神秘命名 (Mysterious Name)** | 函数、变量或类型命名无法表达真实意图 | 重新命名；若想不出清晰名字，说明职责混杂需拆解 |
| **重复代码 (Duplicated Code)** | 相同或相似的逻辑片段出现在多处 | 提炼公共方法，收敛至单点复用 |
| **依恋情结 (Feature Envy)** | 方法频繁调用其他对象的数据而非自身属性 | 将该方法移动至其所依恋的数据对象中 |
| **数据泥团 (Data Clumps)** | 相同的 3~4 个参数总是一起在多个方法间传递 | 封装为独立的值对象 (Value Object / DTO) |
| **基本类型偏执 (Primitive Obsession)** | 滥用字符串或整数代表领域概念（如手机号、金额） | 建立轻量领域值对象，封装校验逻辑 |
| **重复的分支瀑布 (Repeated Switches)** | 相同的 `if-else` 或 `switch` 在多处依据同一类型做分发 | 采用多态模式、策略模式或映射表替代 |
| **散弹式修改 (Shotgun Surgery)** | 一个微小需求变更需要同时修改散落的十几个文件 | 将高内聚变化的逻辑收敛至单一模块 |
| **发散式变化 (Divergent Change)** | 单个类因为多种互不相干的业务理由频繁被修改 | 按职责边界拆分为多个专职类（单一职责原则） |
| **夸夸其谈未来性 (Speculative Generality)** | 为未发生的虚构未来需求预留复杂抽象或钩子 | 果断删除无用抽象，内联为紧凑实现 |
| **过长的消息链 (Message Chains)** | 连续深层导航调用 `a.getB().getC().getD().run()` | 遵循迪米特法则，在首个对象上封装对外服务方法 |
| **中间人委托 (Middle Man)** | 某个类的大多数方法只是毫无价值地透传转发 | 移除中间人，让调用方直接对接真实目标 |
| **被拒绝的遗赠 (Refused Bequest)** | 子类继承了父类却重写覆盖或抛异常拒绝大部分能力 | 将继承关系改为对象组合 (Composition over Inheritance) |

## 3. 现代工程安全与健壮性坏味道

除了传统面向对象坏味道，还需排查现代工程红线：
1. **N+1 查询陷阱**：在 `for` 循环中发起数据库或 RPC 查询，必须改为批量查询；
2. **集合空安全失守**：列表查询无匹配时返回 `null`，必须改为返回空集合（如 `Collections.emptyList()`）；
3. **异常处理吞没**：空的 `catch` 块或仅使用 `e.printStackTrace()` 敷衍，必须有业务语义转换或降级；
4. **日志风暴与裸打印**：使用 `System.out.println` 或裸 `console.log`，必须统一使用工程受管 Logger；
5. **硬编码机密泄露**：代码中包含明文 Token、数据库密码或本地文件绝对路径（`file:///`、物理盘符）。

## 4. 核查打卡清单

- [ ] 是否存在大段重复逻辑？
- [ ] 是否有循环内调用数据库或远程接口？
- [ ] 集合返回值是否彻底杜绝了 `null`？
- [ ] 是否存在未防御的复杂链式空指针隐患？
- [ ] 所有的日志与报错是否语义清晰且无裸打印？
