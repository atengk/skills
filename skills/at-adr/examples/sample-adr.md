# 架构决策记录范例：采用 RocksDB 进程内存储重构分布式会话状态机

- **状态 (Status)**：`Accepted`

- **生效日期 (Date)**：2026-03-20
- **关联 Issue/PR**：Issue #88 / PR #104
- **技术债标记 (Technical Debt)**：存在技术债（初期未实现跨节点数据自动重平衡，依赖上层网关一致性哈希分发）

---

## 2. 上下文与问题陈述 (Context and Problem Statement)

随着反欺诈风控流量激增，实时会话状态机面临严重的性能瓶颈：
- 目前会话状态全部存储在中心化 Redis 集群中，每次风控判定需要往返网络 4~6 次；
- 在高峰期（20 万 QPS），网卡软中断与网络往返（RTT 约 3~5ms）占用了整个判定周期的 70% 耗时；
- 架构委员会期望将单次风控状态校验整体 P99 延迟从 35ms 压降至 5ms 以内，且在突发断网分区时具备本地只读自愈能力。

---

## 3. 决策驱动力 (Decision Drivers)

1. **超低延迟 (Sub-millisecond RTT)**：单次状态读写必须在微秒级（< 1ms）内完成；
2. **高吞吐局部性**：支持单机 30 万 QPS 混合读写，不受宿主机网卡带宽瓶颈牵制；
3. **内存与磁盘分级**：内存预算受限（每节点仅 16GB RAM），但需容纳 500GB 历史会话特征数据；
4. **零网络跳数 (Zero-Network Hops)**：读写完全在进程内存或本地 NVMe SSD 完成。

---

## 4. 考虑的选项列表 (Considered Options)

- **选项 1**：引入 RocksDB（C++ 嵌入式引擎，Java JNI 接入）；
- **选项 2**：继续扩容独立 Redis Cluster 分片至 64 节点；
- **选项 3**：使用纯 JVM 进程内堆外缓存（如 Chronicle Map）。

---

## 5. 决策结论与核心理由 (Decision Outcome)

- **最终裁决**：选择 **选项 1：引入 RocksDB 作为本地进程内嵌入式 KV 引擎**。
- **核心理由**：
  - 基于 LSM-Tree 架构，能够充分利用本地 NVMe SSD 的高顺序写入吞吐，打破 JVM 堆内存大小限制；
  - 进程直接通过 JNI 与本地共享内存交互，彻底抹平了跨网络 TCP 握手与序列化反序列化延迟；
  - 拥有极佳的成熟度与生态验证（被 Kafka Streams、Flink、TiKV 广泛检验）。

---

## 6. 正负后果与权衡评估 (Consequences)

### 正面后果 (Positive Consequences)
- **时延断崖式降低**：本地读写 P99 降至 0.4ms，整体风控判定耗时从 35ms 锐减至 3.2ms；
- **成本显著节约**：直接下线了 48 台外置 Redis 独立实例节点，月度基础设施开销缩减 60%；
- **可用性提升**：即使机房核心交换机抖动，本地状态机仍可依靠本地全量特征实现降级打分。

### 负面后果与妥协 (Negative Consequences & Risks)
- **部署模式变为有状态 (Stateful)**：Pod 滚动升级时需要挂载持久化云盘（PVC），扩缩容耗时增加；
- **运维心智负担**：需要 SRE 针对 LSM-Tree Compaction 参数（如 write_buffer_size、max_write_buffer_number）做深度调优；
- **纳管技术债**：当前节点缩容时不支持存量数据热迁移，需在下一季度开发基于一致性哈希的状态平滑接管组件。

---

## 7. 候选选项利弊详查 (Pros and Cons of the Options)

### 选项 1：RocksDB 嵌入式引擎 (选定)
- **优点 (Good)**：微秒级时延、支持海量超出内存的数据持久化、写入吞吐极高。
- **缺点 (Bad)**：需要管理 JNI 堆外内存泄露风险，增加了容器部署有状态复杂性。

### 选项 2：继续扩容 Redis Cluster
- **优点 (Good)**：服务保持无状态、运维现成且无需改造容器交付流水线。
- **缺点 (Bad)**：网络 RTT 物理瓶颈无法突破、内网带宽打满风险依然存在、成本极度高昂。

### 选项 3：Chronicle Map 堆外内存
- **优点 (Good)**：纯粹的内存级交互，读写速度最快。
- **缺点 (Bad)**：必须全量放入 RAM，面对 500GB 数据量内存成本完全失控，且断电持久化恢复极慢。
