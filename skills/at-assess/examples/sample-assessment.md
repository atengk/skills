# 可行性评估实战案例：引入 GraphQL 替代 RESTful 网关评估 (Sample Assessment)

本文档呈现了一个针对“是否在现有电商系统全面引入 GraphQL 替代 RESTful 开放网关”的真实可行性预研报告。

---

# 方案可行性评估报告：全量引入 GraphQL 替代 REST 接口评估 (Feasibility Assessment)

> **评估标识**：`ASSESS-20261012-GRAPHQL-MIGRATION`
> **提案类型**：`ARCHITECTURE_CHANGE`
> **涉及系统**：API 网关与 C 端核心用户服务
> **评估时间**：2026-10-12
> **裁决结论**：**🔴 STOP (果断止损，不予立项)**

---

## 1. 提案概述与核心目标

- **提案动因**：移动端前端同学反馈目前首页需调用 4 个 REST 接口拼装数据，网络时延较高，希望引入 GraphQL 实现“按需拉取字段与单次请求多资源聚合”；
- **提案设想**：在现有 Spring Boot 3.3 架构上引入 `spring-boot-starter-graphql`，搭建统一 Schema 并开放 `/graphql` 端点。

---

## 2. 五维量化评估矩阵

| 评估维度 | 评分 (1~5 分) | 核心判定表现 | 风险与代价考量 |
| :--- | :---: | :--- | :--- |
| **1. 技术可行性** | 3/5 | Spring for GraphQL 支持成熟 | 现有 MyBatis-Flex 批量关联难以直接映射复杂 Resolver |
| **2. 改动复杂度** | 2/5 | 侵入式极强，需重写所有 DTO | 爆炸半径覆盖整个 C 端展示层数十个接口 |
| **3. 安全与合规** | 2/5 | 极高 DoS 风险 | 客户端可构造深层嵌套循环查询；需额外配置查询复杂度限制 |
| **4. 维护与运维** | 2/5 | APM 监控黑盒化 | 所有请求均为 `POST /graphql`，HTTP 状态码全为 200，网关与 SkyWalking 链路排障极难定位 |
| **5. 投入产出比** | 2/5 | ROI 严重倒挂 | 预估重构耗时 1.5 人月，仅优化首屏 30ms，新增风险与收益不匹配 |

---

## 3. 确凿证据链与致命缺陷分析

1. **APM 监控与网关安全防护失效**：
   - 当前网关依赖基于 URI 路径（如 `/api/v1/orders`）进行速率限制（Rate Limiting）与 WAF 防护；
   - 切换为单一 `/graphql` 端点后，现有限流与熔断规则完全瘫痪，缺乏字段级鉴权基础设施。
2. **N+1 数据查询炸弹**：
   - 在 GraphQL 解析 `User -> Orders -> OrderItems` 嵌套树时，若无复杂的 DataLoader 批处理，会触发海量循环 SQL 查询，压垮 MySQL 数据库。

---

## 4. 最终裁决与替代方案

### 4.1 裁决结论
> **最终裁决**：**🔴 STOP (终止立项)**
> **核心理由**：改造成本与监控运维风险过高，且容易在核心主链路引入安全与性能暗坑，投入产出比极低。

### 4.2 推荐轻量级替代方案
- **建议方向**：维持现有 RESTful 架构，在 API 网关层或现有 Controller 中提供专门的聚合端点 `GET /api/v1/home/aggregate`，单次批量下发首页所需资源；
- **预期收益**：达成相同的首屏合并请求效果，开发周期仅需 1 天，零架构震荡。
