# Git Worktree 物理环境隔离与生命周期管理协议 (Worktree Management Protocol)

本协议规范了在 AI Agent 辅助软件研发过程中，利用 Git Worktree 实现物理级环境隔离的标准流程。通过将新特性开发、破坏性试验或紧急热修隔离在独立的工作树中，彻底杜绝污染当前工作区与主干分支，并在遇到环境重型依赖时提供平滑降级机制。

## 1. 物理目录拓扑与命名规范

为避免将工作树嵌套在当前仓库内部导致构建工具循环扫描或 Git 忽略规则失效，统一采用同级目录拓扑：

```text
<workspace-parent>/
├── <repo-name>/                 # 主仓库目录 (主干/当前开发工作区)
└── <repo-name>-worktrees/       # [推荐] 统一的工作树容器父目录
    ├── feat-<feature-name>/     # 特性隔离工作树
    └── fix-<hotfix-name>/       # 热修隔离工作树
```

### 命名约束
- **目录标识**：必须遵循 kebab-case 规范，格式为 `<type>-<name>`（如 `feat-order-export`、`fix-token-refresh`）；
- **专用容器**：严禁直接在主仓库根目录下创建未经 `.gitignore` 保护的子工作树；优先创建在主仓库同级目录 `<repo>-worktrees/` 下，确保物理解耦。

## 2. 环境沉重度探查与平滑降级机制

虽然 Git Worktree 提供了强物理隔离，但在某些重型工程中盲目创建 Worktree 会导致磁盘暴增、IDE 重复建立索引卡死。创建前必须执行环境沉重度探查：

### 2.1 三大沉重度风险指标
1. **未共享巨型依赖 (Giant Unshared Dependencies)**：
   - 项目中存在无法共享的数 GB 级依赖目录（如未启用 pnpm 共享 store 的 npm/yarn `node_modules`、大型 Python 虚拟环境或 C++ 重型编译中间产物）；
   - 新建工作树意味着必须重新完整安装一份依赖，显著浪费磁盘空间与网络带宽；
2. **复杂 Git 子模块 (Complex Submodules)**：
   - 仓库依赖嵌套或大量的 Git Submodule（`.gitmodules`），检出和递归同步耗时极长；
3. **脏工作区与未跟踪资产 (Dirty Working Tree)**：
   - 主工作区存在大量未跟踪的大型数据文件或未提交的复杂临时改动。

### 2.2 平滑降级策略 (Graceful Branch Fallback)
- **主动预警**：当命中上述任意风险时，Agent 必须主动向开发者汇报环境沉重度风险；
- **一键平滑降级**：优先建议放弃物理 Worktree 隔离，平滑降级为常规本地分支：
  ```bash
  git checkout -b feature/<name>
  ```
  在保持原有依赖与 IDE 索引不重建的前提下展开特性研发；
- **显式确认原则**：仅当开发者明确确认“需要独立 Worktree”且环境具备足够资源时，方可继续推进 Worktree 创建。

## 3. 分支生命周期与创建流程

### 3.1 状态预检与目标分支判定
1. **主仓库干净度核验**：创建前运行 `git status`，记录主仓库当前未提交改动（如有未暂存改动，提示用户或选择通过 Worktree 隔离开发）；
2. **分支冲突防范**：
   - 检查本地与远端是否已存在同名分支；
   - 若拟基于既有远程分支开发：`git worktree add <path> <branch>`；
   - 若创建全新特性分支：`git worktree add -b <new-branch> <path> <base-ref>`（默认以最新的主干 `origin/main` 为基准）。

### 3.2 跨分支复用保护
- Git 不允许两个工作树同时检出同一个分支。若目标分支已被检出，必须先确认既有工作树的归属或切换分支，严禁强行解绑导致未提交数据丢失。

## 4. 依赖安装与环境初始化契约

新工作树创建后，属于纯净的代码检出状态，必须完成环境初始化方可开始研发：

### 4.1 环境变量与本地配置对齐
- **敏感配置继承**：从主仓库安全复制 `.env.local`、`.env.example` 或未被 Git 跟踪的本地配置文件；
- **配置隔离**：检查端口与数据库连接，确保隔离工作树启动的本地服务不与主工作区端口产生冲突（如支持动态端口偏移）。

### 4.2 依赖安装安全纪律
- 根据项目类型执行受控的确定性安装命令（例如 Node.js 项目使用 `npm ci` 或 `pnpm install --frozen-lockfile`，Python 项目激活专属虚拟环境或使用 `poetry install`）；
- 严禁在未经锁定依赖版本的情况下执行破坏性依赖升级。

## 5. 测试基线核验红线

在隔离工作树中编写任何业务代码之前，**必须建立绿灯测试基线 (Green Baseline)**：

1. **执行基线测试套件**：运行工程既有的单元测试与语法检查；
2. **记录基线状态**：确认当前从基准分支切出的代码处于 100% 测试通过状态；
3. **前置阻断机制**：若基准测试本身失败，立即中断后续特性开发，向用户告警并优先修复基线或切换基准提交点。

---

## 6. 完工合并、收尾与清理协议

当隔离工作树中的开发与测试验证全部通过后，执行严密的生命周期闭环：

### 6.1 成果移交与审查
- 确认隔离工作树内所有变更均已通过测试并规范提交；
- 向用户展示完成成果与分支 Diff 概况，等待用户确认合并方式（PR 提交 / 主干合并 / 保留待审）。

### 6.2 安全清理标准工序
1. **切离工作树**：终端工作目录切回主仓库根目录；
2. **安全移除**：执行 `git worktree remove <path>`；
3. **元数据修剪**：执行 `git worktree prune` 清理孤儿索引；
4. **分支收尾**：若分支已成功合并入主干，按需删除本地已合入分支；若废弃试验，提示用户后删除对应分支；
5. **残留检查**：核查磁盘物理目录是否已干净移除，避免遗留大容量 `node_modules` 或构建产物。

## 7. 跨平台兼容与安全避坑指南

- **Windows 路径超长保护**：Windows 下优先采用简短的工作树目录名，防范 `MAX_PATH` 260 字符溢出；
- **路径反斜杠转换**：脚本中一律使用标准正斜杠 `/` 或 `pathlib.Path` 处理跨平台路径；
- **文件锁释放防范**：在 Windows 系统执行 `git worktree remove` 前，确保 IDE、终端或语言服务已释放对该工作树目录内文件的句柄占用；
- **零绝对路径规范**：所有向用户呈现的报告与文档，均使用相对路径或无盘符标识，杜绝硬编码绝对路径泄漏。
